# AGENTS.md

This file provides guidance to agents when working with code in this `projects/cli` package.

## Project Overview

`cradle` is a runtime for portable agents defined as folders (see the repo-root [`ARCHITECTURE.md`](../../ARCHITECTURE.md) for the folder format spec). `cradle run <dir>` reads an agent folder — `SYSTEM.md` or `APPEND_SYSTEM.md` (at least one) plus optional pi-native `settings.json`/`models.json`, `skills/`, `extensions/`, `sandbox/nono.json`, `sandbox/sbx.json`, `schedule/` — and launches the [pi](https://github.com/earendil-works/pi-mono) coding agent configured from it. Two sandbox backends: a folder declaring `sandbox/nono.json` is wrapped in the [`nono`](https://github.com/nolabs-ai/nono) filesystem sandbox via `nono run`; a folder declaring `sandbox/sbx.json` (or a run passing `--sandbox-backend sbx`) runs pi inside a [Docker Sandboxes](https://docs.docker.com/ai/sandboxes/) microVM via `sbx exec` after a create/policy/provision setup sequence (`src/sbx/compose.ts` composes it; `commands/run.ts` runs it). Bun runs TypeScript natively (no compile step for dev) and compiles the CLI into standalone platform-specific binaries that deploy statically with the docs site, installed via `curl -fsSL https://coryrylan.github.io/cradle/install.sh | bash` (the primary install path; the npm package `@coryrylan/cradle` is the alternative). Shelling out to `nono`/`sbx` (rather than embedding a native addon) keeps the binary a clean `bun build --compile` target on every platform.

## Architecture

- **Entry**: `src/index.ts` (shebang `#!/usr/bin/env bun`) → imports `src/cli.ts`, which wires the commands via Yargs.
- **Commands** (`src/commands/`): `start` (resolve the ref — bare alias name or path, see `agent/aliases.ts` — → load agent folder → generate extensions → when `sandbox/nono.json` is present, generate the per-agent nono profile → compose the pi/nono argv → spawn), `doctor` (probe `pi` (required), `nono` (recommended and required only for a nono-backend run), `sbx` (recommended and required only for an sbx-backend run; it has no `--version` flag, so its version is read via the `sbx version` subcommand), and `mise` (recommended — cradle never invokes it, but resolves pi/nono from its shims and the sandbox profile assumes its layout); only missing `pi` fails its exit code; each found bin's version output is probed and reported alongside its resolved path). There is no standalone `setup` command: the nono-presence check (`requireBin('nono')`) and the per-agent profile generation happen inline only for sandboxed `cradle run` runs.
- **Agent folder runtime** (`src/agent/`) — the core of the package:
  - `aliases.ts` — resolves a `cradle run <ref>` reference into a folder path before `folder.ts` loads it. A bare name (no path separators, not `.`/`~`-led) is looked up in a global alias table at `<home>/.cradle/settings.json` (`{"agents": {"name": {"path": "/abs/..."}}}`); anything already path-shaped is never an alias lookup. `commands/run.ts`'s `planRun` calls `resolveAgentRef` first, so the resolved absolute path is what `loadAgentFolder`, `stateDirFor`, and the generated nono profile all see — `cradle run my-agent` and the equivalent absolute path share one state dir. This table is config, not state: its path derives from `home` only, entirely apart from `CRADLE_STATE_DIR` (the state root, `src/agent/state.ts`). Malformed JSON is a hard error; a malformed alias entry warns and drops (cradle is this file's schema authority, unlike an agent folder's own pi-native `settings.json`).
  - `folder.ts` — loader/validator. The system prompt comes from `SYSTEM.md` (→ `AgentFolder.systemFilePath`, mapped to `--system-prompt` — REPLACES pi's default prompt) and/or `APPEND_SYSTEM.md` (→ `appendSystemFilePath`, mapped to `--append-system-prompt` — appends to it); each field is `string | null` and the loader requires at least one non-null, so a folder with neither, and malformed JSON, are hard errors (a legacy `AGENTS.md` gets a rename hint to `APPEND_SYSTEM.md`); everything else unexpected (unknown files, reserved dirs) is a warning + continue. `sandbox/nono.json` supports `sandbox` (boolean opt-out, folded into `AgentSandbox.posture: 'unconfigured' | 'enabled' | 'disabled'` — a missing `sandbox/nono.json` is `'unconfigured'`, a present file without `"sandbox": false` is `'enabled'`, `{"sandbox": false}` is `'disabled'`), `network` (→ `AgentSandbox.network`: a curated subset of nono's canonical profile `network` keys — `block`/`network_profile`/`allow_domain`/`open_port`/`listen_port` → camelCased `AgentNetwork`; warn-and-drop malformed entries; folded into the generated profile's `network` block by `profiles.ts`, disclosed by nono's banner under `--verbose`; a lingering `net` key gets a targeted `"net" was removed — use "network"` hint, mirroring the `AGENTS.md` rename hint), `filesystem` grants (`read`/`write`/`allow` plus nono's direct-child `unix_socket_dir_bind`, all folded into the profile and disclosed by nono's banner under `--verbose`), and `unsafe_macos_seatbelt_rules` (array of raw Seatbelt s-exprs → `AgentSandbox.unsafeMacosSeatbeltRules`; each must be parenthesized — `readSeatbeltRules` warns+drops the rest, mirroring `readStringList`'s path guard; merged after the base's rules in `profiles.ts`; nono's banner does NOT list seatbelt rules — audit them in the folder's `sandbox/nono.json` or the generated profile). The `allow` + `unix_socket_dir_bind` grants on `~/.agent-browser`, `open_port: [0]` for Chrome's random localhost DevTools port, two-rule set `(allow mach-register)` + `(allow iokit-open)`, and the sandbox-only generated `agent-browser-nono-fallback.ts` extension are what let agent-browser + Chrome run sandboxed. The fallback appends Chrome's `--no-sandbox` argument on macOS and maps nono's dynamically injected proxy to `AGENT_BROWSER_PROXY` on every platform; unsandboxed runs never load it — see the CLI README / `examples/browser`. `sandbox/sbx.json` is the sibling opt-in for the sbx backend (→ `AgentFolder.sbx`, same `AgentSandbox` shape): a restricted subset of nono.json's schema (`sandbox` opt-out, `filesystem` `read`/`write`/`allow`, `network` `block`/`allow_domain`) where the nono-only keys (`unix_socket_dir_bind`, `network_profile`, `open_port`, `listen_port`, `unsafe_macos_seatbelt_rules`) warn-and-drop with dedicated "nono-only" messages (`readSbxSandbox`/`warnNonoOnlyKey`) — the VM boundary has no equivalent. Backend precedence (resolved in `commands/run.ts` `resolveBackend`): `--no-sandbox` (off) > `--sandbox-backend <nono|sbx>` (that backend, forced on) > `--sandbox` (folder preference, default nono) > folder postures (both files `'enabled'` → nono wins with a warning naming the `--sandbox-backend sbx` override) > restrictive network flags (`--offline`/`--allow-host`, which force nono on — requesting a network policy is only enforceable inside a sandbox) > unsandboxed default. A posture of `'unconfigured'` (no `sandbox/nono.json`) or `'disabled'` (folder opt-out) appends a loud warning to the plan; a `sandbox/` dir with no `nono.json` warns at load too. Network precedence (also `commands/run.ts` `resolveNetwork`): `--offline` (→ `{block:true}`) > `--allow-host <host>` (repeatable → `{allowDomain}`) > folder `network` > open default (no `network` block emitted); CLI flags REPLACE the folder network (no merge). `--offline`/`--allow-host` force the sandbox on (same as `--sandbox`) unless `--no-sandbox` is also passed, in which case cradle warns `network policy has no effect without the sandbox — pi runs with no network isolation (--sandbox to enforce it)` and nothing is enforced. nono is the enforcement authority and fails closed (bad key or unenforceable platform → refuses to start), so there is NO cradle-side network fallback. v1 honors `settings.json`'s `defaultProvider`/`defaultModel`/`defaultThinkingLevel` and passes `models.json`'s `providers` object through near-opaquely (pi is the schema authority) — the one normalization is filling pi's zero-cost default for models without a `cost`, because pi's models.json loader defaults it but `registerProvider` crashes the turn without it (`model.cost.input`, found live). `settings.json` is a pi-native file (pi owns its schema), but pi never reads the agent folder's copy — keys cradle doesn't map (`theme`/`quietStartup`/`collapseChangelog`/…) have no effect and warn as ignored (`warnUnmappedSettingsKeys` names where pi does read them; `MAPPED_SETTINGS_KEYS` is the authoritative set) — with two keys handled cradle-side rather than mapped to flags: `packages` (pi's npm-distributed extension mechanism, e.g. `"packages": ["npm:pi-example-tool"]`, or pi's object form `{"source": "npm:pi-example-tool", "extensions": ["*.ts"]}`) is parsed by `agent/packages.ts`'s `readPackageSpecs` (npm: sources only — `git:`/`https:`/`ssh:`/local-path sources are warned and dropped; the object form's `extensions` patterns and `autoload: false` ride onto the spec, its sibling `skills`/`prompts`/`themes` filters warn as undelivered since cradle passes a package's extensions and nothing else) and resolved/installed by `commands/run.ts` into a per-agent npm project, with each package's selected entry files passed as explicit `-e` flags (pi loads explicit `-e` paths even under `--no-extensions`). Package extension discovery mirrors pi's order — manifest `pi.extensions` entries (file, directory, or glob, then the manifest's own `!`/`+`/`-` overrides), else a convention `extensions/` dir, else a top-level `index.ts`/`index.js` — and `agent/package-filters.ts` (pi's pattern vocabulary: plain glob includes, `!` excludes, `+`/`-` force an exact path in or out; `applyDeltaPatterns` is the `autoload: false` variant where only named patterns load) narrows it to what the settings entry selected, with an empty `extensions: []` selecting nothing, silently; `npmCommand` selects the installer cradle shells out to for that install (default `npm`; must be a single-element array naming one of `npm`/`pnpm`/`yarn`/`bun` — a bare command, no paths/flags/extra argv, since this install runs on the host before the sandbox spawns and folder-controlled argv there is a host-code-execution vector — anything else warns and falls back). `extensions/` enumeration mirrors pi's own discovery shapes (top-level `*.ts` plus each subdir's `index.ts`).
  - `schedules.ts` — loader for `schedule/*.md`, the cron-driven runs (`AgentFolder.scheduleDir` resolves the directory; parsing is LAZY, so `cradle run` pays one `stat`, not N file reads). Each file is YAML frontmatter (`cron`, `cwd` required; `name`, `description` optional) plus a markdown body that becomes the prompt, parsed with the built-in `Bun.YAML.parse` — no dependency, the package's only runtime dep is still yargs. Unlike `folder.ts`'s single-file loaders, a malformed entry warns-and-drops rather than throwing: this is a COLLECTION (the `packages.ts` precedent), and one broken schedule must not hide the rest. The filename is the identity (`daily-report.md` -> `daily-report`) and is shape-guarded like `aliases.ts`'s `BARE_NAME`, because it becomes a launchd label and a systemd unit name. `cwd` is `isPathShaped`-guarded then `expandHome`d; a bare `cwd: ~` is YAML NULL, not the home dir, so that case gets its own targeted hint rather than the generic path warning. Symlinked `.md` files are followed, matching the folder format's symlink tolerance for `skills/`.
  - `state.ts` — per-agent runtime state lives OUTSIDE the portable folder, under `~/.cradle/agents/<basename>-<sha256(absPath)[0..8]>/` (`CRADLE_STATE_DIR` overrides the root): `extensions/` (regenerated every run; includes the sandbox-only agent-browser nono fallback and providers when configured), `sessions/` (never wiped), `nono-profile.json` (the generated per-agent sandbox profile, rewritten every run), `mise-cache/` (sandboxed runs' private `MISE_CACHE_DIR`, created lazily by mise — see `launch.ts`'s `composeEnv`), and — only when the folder declares settings `packages` — `npm/` (a private npm project `commands/run.ts` installs into via `PackagesPlan`; reinstalled only when its generated `package.json` changes or `node_modules` is missing).
  - `extensions/` — source for the generated pi extension: `providers.ts` exports the `emitProvidersExtension` string emitter (one `pi.registerProvider` per models.json provider, config baked in verbatim).
  - `launch.ts` — argv + spawn-env composition, keyed on `LaunchSpec.backend: 'nono' | 'sbx' | null`. `composePiArgv` builds the explicit pi invocation; `composeArgv` wraps it in `nono run --silent --profile <generated-profile>` for the `'nono'` backend (silent mode suppresses nono's startup banner; `--verbose` drops `--silent` to show the capabilities banner, and cradle prints `🔒 Sandbox Active` — `(sbx)`-suffixed on sbx runs — on silent sandboxed runs) and returns the bare pi argv for `'sbx'` and `null` — the sbx `sbx exec` wrapper is composed at materialization in `commands/run.ts`, not here. All nono filesystem grants (cwd, agent dir, state dir, and the agent's `sandbox/nono.json` extras) AND the resolved network posture live INSIDE the generated profile (`nono/profiles.ts`), not as flags. Both `nono` and `pi` run by their resolved paths (mise shim may not be on PATH yet; the base profile grants the mise tree so the resolved pi path works inside the sandbox too) — EXCEPT under `'sbx'`, where `piBin` is the literal `pi`: host paths are meaningless inside the microVM, and provisioning installs pi on the guest PATH. `composeEnv` composes the spawn env — `{ MISE_CACHE_DIR: <state>/mise-cache }` on nono runs, `{}` otherwise (the sbx guest has no mise; its `HOME` override rides the exec argv — see the argv bullet below for why).
- **Everything rides on argv — never env vars, never files inside `~/.pi/agent`.** The one deliberate exception: sandboxed runs export `MISE_CACHE_DIR=<state>/mise-cache` (mise config, not pi config — see `composeEnv` in `agent/launch.ts`; keeps the sandbox-denied shared mise cache from spamming `failed to write cache file` warnings while closing the cache-poisoning vector a shared, sandbox-writable `bin_paths` cache would open). The agent folder maps to pi flags: `SYSTEM.md` → `--system-prompt <path>` (replaces pi's default prompt) and/or `APPEND_SYSTEM.md` → `--append-system-prompt <path>` (appends to it) — pi's own system-prompt-file names; the folder mirrors `~/.pi/agent`'s layout, but pi only discovers them in `<cwd>/.pi/` or its agent dir, so cradle passes the paths explicitly (both flags ride together when the folder ships both, pi using SYSTEM.md as the base with APPEND_SYSTEM.md appended; pi reads a flag value as a file when it's an existing path); settings keys → `--provider`/`--model`/`--thinking` (always passed explicitly when the agent defines them, so personal pi defaults never bleed into model selection); sandboxed runs → generated `-e` agent-browser/nono environment fallback; `models.json` → generated `-e` providers extension; settings `packages` → a per-agent npm project at `<state>/npm`, installed via the folder's `npmCommand` (default `npm`) before the sandbox spawns, each package's `package.json` `pi.extensions` entries passed `-e` after cradle's generated extensions and before the folder's own extensions; `extensions/` → `-e <file>` verbatim, ordered LAST among the `-e`s so agent extensions load with providers registered, sandbox subprocess compatibility configured, and any package-provided tools already available (custom tools live here too, via `pi.registerTool`); `skills/` → `--skill <dir>`; sessions → `--session-dir <state>/sessions`; isolation from the personal pi config → `--no-extensions --no-skills --no-prompt-templates` (explicit `-e`/`--skill` still load; `--no-context-files` is deliberately NOT passed — the target project's AGENTS.md/CLAUDE.md context is desirable). Passthrough after `--` lands last so user flags win under pi's last-wins parsing. Accepted v1 leaks: pi still reads the personal `~/.pi/agent/settings.json` (cosmetics), shares `auth.json`, and writes trust decisions to the personal `trust.json`; `--no-extensions` also disables the personal `~/.pi/agent/settings.json`'s own `packages` inside agent runs — personal `~/.pi/agent` packages still never load, distinct from the agent folder's own `packages`, which cradle resolves itself (intentional isolation). The personal `~/.pi/agent/{SYSTEM,APPEND_SYSTEM}.md` and project `.pi/{SYSTEM,APPEND_SYSTEM}.md` do NOT leak in: a CLI `--system-prompt`/`--append-system-prompt` replaces pi's own discovery of that file entirely (`systemPromptSource ?? discoverSystemPromptFile()` and `appendSystemPromptSource ?? discoverAppendSystemPromptFile()` in pi's resource-loader).
- **nono profile — per-agent, generated** (`src/nono/cradle-pi.json` is the embedded BASE, imported `with { type: 'json' }` by the co-located `src/nono/profiles.ts`): there is NO shared global profile in `~/.config/nono/profiles/`. Instead `profiles.ts` `buildProfileJson` (pure, unit-tested) merges the base — which `extends` the built-in `default`, adds the `node_runtime` + `git_config` + `unlink_protection` groups (git identity/config and gh auth aren't in nono's `default`; `unlink_protection` blocks deletion outside user-writable grants), read grants for mise's install/config/state trees (state holds mise's trust db — unreadable trust records make sandboxed mise treat every `mise.toml` as untrusted) and `$HOME/.config/gh` (gh CLI auth), `$HOME/.pi/agent` allow, `$HOME/.agents` read, and the macOS `say` grants — with THIS run's grants: cwd (`allow`), agent dir (`read`), state dir (`allow`), the linked git dir when cwd is a worktree/submodule checkout (`allow`, resolved by `nono/linked-git-dir.ts`), the agent's own `sandbox/nono.json` entries (`~`/`$HOME` expanded via `expandHome`), and its `unsafe_macos_seatbelt_rules` appended after the base's `unsafe_macos_seatbelt_rules` (Seatbelt is last-match-wins). `materializeRun` writes the result to `<stateDir>/nono-profile.json` on sandboxed runs; `agent/launch.ts` passes it as `nono run --profile <that file>` (nono accepts a profile by file path, and `extends`/`groups` still resolve from its registry). `meta.name` is derived per-agent from the state-dir basename (`cradle-<name>-<hash>`) so no two agents share a profile identity. The resolved `network` posture (`toNonoNetwork` maps camelCase `AgentNetwork` → nono's snake_case `network` keys) is emitted as the profile's `network` block when present (absent ⇒ no block ⇒ nono default open); nono enforces it and fails closed on a bad key — no `--block-net` flag. Keep `allow` paths tight: nono refuses to start if a grant overlaps its protected state root (`~/.local/state/nono`), so never grant `/Users` or `~/`. Each agent's sandbox posture is thus fully described by its own directory (base + `sandbox/nono.json`) — the `--dry-run` write plan shows the profile path, and the composed command is a single `--profile` line.
- **sbx backend — per-run composed, imperative setup** (`src/sbx/compose.ts`, pure and unit-tested like `nono/profiles.ts`): `composeSbxMounts` builds the guest mount list (cwd rw, agent dir ro, state dir rw, `$HOME/.pi/agent` rw — pi auth/settings carry over via the exec `HOME` override, OAuth refreshes write back to the host; linked git dir rw; `sandbox/sbx.json` grants read→ro, write/allow→rw; rw beats ro on dedupe), `sbxSandboxName` derives `cradle-<stateDirBasename>-<hash8>` from the sorted mount set (mounts are fixed at sbx creation, so a changed mount set gets a fresh sandbox instead of silently attaching to stale mounts), and the `composeSbx*Argv` family emits the `sbx create shell`/`sbx policy`/provision (`npm i -g @earendil-works/pi-coding-agent`, pinned to the host pi version via `MaterializeDeps.readPiVersion`)/`sbx exec -i [-t] -e HOME=<home> -w <cwd>` argvs. `materializeRun` runs the setup via `MaterializeDeps.run` (`util/proc.ts` `runCapture`): create tolerates an "already exists" stderr (`isSbxAlreadyExistsError` — attach), policy rules are idempotent re-adds, provision must exit 0. Network translation encodes verified sbx semantics: `block` → per-sandbox `deny **` (beats allows at the same scope, so block and allowlist never co-emit); `allow_domain` entries expand to `d,*.d` (sbx matches exact host and subdomains as disjoint resources), bare IPv4s stay bare, and `localhost`/`127.0.0.1` become `host.docker.internal` (guest loopback is the VM) — the generated providers extension rewrites localhost baseUrls the same way under sbx (`emitProvidersExtension`'s `rewriteLocalhostBaseUrls` option). Per-sandbox allows ADD to the user's global sbx policy and cannot subtract — `sbxNetworkWarnings` discloses that on every allowlist run (strict allowlists need a global `sbx policy init deny-all`).
- **Scheduled runs — `schedule/` compiled to native OS timers** (`src/schedule/`, pure and unit-tested like `nono/profiles.ts`; driven by `src/commands/schedule.ts`): `cron.ts` owns cron syntax and semantics so the two emitters can never disagree — `parseCron` normalizes each field to a sorted value list or `null` ("every"), expands `@hourly`/`@daily`/`@weekly`/`@monthly`/`@yearly`, accepts day/month names, and HARD-REJECTS an expression constraining both day-of-month and day-of-week (cron ORs those two fields; launchd and systemd both AND them, so there is no faithful encoding on either backend — rejecting once here is what keeps the emitters honest). `nextFire` steps coarsely (day -> hour -> minute) via local-component `Date` construction so month rollover and DST gaps resolve through the platform's own calendar math, bounded at 366 days so a never-fires expression (Feb 30) returns `null` instead of spinning. `timer.ts` holds the shared `TimerPlan` contract (`id`, `files`, `installSteps`, `removeSteps`; a step carries `ignoreFailure` for the bootout/disable that legitimately fails on a first install) so the command layer dispatches on platform exactly once. `launchd.ts` emits the LaunchAgent plist at `~/Library/LaunchAgents/com.cradle.<agentId>.<slug>.plist` — `StartCalendarInterval` is the cartesian product of only the CONSTRAINED fields (an omitted key means "every"; all-unconstrained yields the single empty dict), capped at 500 dicts so a pathological expression can't write a multi-megabyte plist, with `&`-first XML escaping and an explicit `PATH` because launchd loads no shell profile. `systemd.ts` emits the `.service`/`.timer` pair under `~/.config/systemd/user/` using native `OnCalendar=` (no expansion needed) plus `Persistent=true`, systemd's equivalent of launchd's wake catch-up; `%` doubles to `%%` (specifier expansion), a raw newline is rejected, and ExecStart arguments are quoted because command lines are the one unit setting systemd tokenizes on whitespace — single-value settings like `WorkingDirectory` take the rest of the line verbatim and must NOT be quoted. Both backends invoke `cradle schedule run <folder> <slug>`, which routes straight into `commands/run.ts`'s ordinary pipeline (`cli.ts` dispatches the `run` action there rather than into `commands/schedule.ts`, which owns only list/install/remove) — so a scheduled run adds NO new sandbox policy: the task's `cwd` becomes the plan's cwd and therefore the profile's cwd grant, exactly as an interactive run in that directory would.
- **`src/setup/`**: platform-independent fs/text helpers, all unit-tested. `install.ts` = idempotent tree writes (`installTree` is what `commands/run.ts` uses to materialize generated extensions); `utils.ts` = small helpers (`isRecord`/`parseJson`/`quoteCommandPart`/error helpers). The macOS dev-environment orchestration (`dev-env.ts`/`env.ts`, brew casks + mise toolchain) that once lived here was removed along with the `setup` command.
- **Embedded resources**: assets co-located with their consumers and inlined into the bundle at build time via import attributes, so they survive `bun --compile` and the ESM bundle with no sidecar files or runtime path resolution. JSON assets import their parsed content (`nono/cradle-pi.json` via `with { type: 'json' }` — the base that `nono/profiles.ts` merges per-agent grants into and re-serializes per run).
- **Testability split**: every module except `util/proc.ts` (real `Bun.spawn`) and `cli.ts` (Yargs wiring) is pure/dependency-injected and unit-tested in-process. `cli.ts` is exercised only via the subprocess smoke tests in `src/index.test.ts`; `util/proc.ts` also has direct tests (`proc.test.ts`) that really spawn trivial commands (`true`, `sh -c`) — no mocks, but keep new spawn/wiring logic thin and out of the in-process import graph of the pure modules. `commands/run.ts` splits into `planRun` (composition, injectable `which`/`cwd`/`home` — builds the profile content via pure `buildProfileJson`) and `materializeRun` (real fs against temp dirs in tests; writes the generated extensions + `nono-profile.json` under the `CRADLE_STATE_DIR`-controlled state dir, so tests never touch a real global path).
- **Package name**: `@coryrylan/cradle`. **Bin name**: `cradle` (what users type). Don't conflate the two.
- **Module system**: ES modules (`type: "module"`). Relative imports use `.js` extensions even for `.ts` sources (standard ESM/TS convention).
- **Task runner**: [Wireit](https://github.com/google/wireit) wraps every npm script for dependency tracking and caching — always invoke via `bun run <script>`, not directly.
- **Lint**: ESLint runs per-package (`bun run lint`). [Knip](https://knip.dev) is configured at the monorepo root (`knip.config.js`, note `ignore: ['examples/**']` and `ignoreExportsUsedInFile`) and runs across all workspaces via `bun run lint:knip` from the repo root.

## Common Commands

Run from `projects/cli/` (wireit-wrapped scripts must run inside the package — bun's `--filter` runner is not wireit-compatible):

```bash
bun install                  # Install deps (resolves at workspace root)
bun start                    # Run the CLI (via wireit: `bun src/index.ts`)
bun src/index.ts <args>      # Run CLI directly with args
bun run lint                 # ESLint (typescript-eslint strict) for this package
bun run test                 # Run all tests
bun run test:coverage        # Run tests with coverage; enforces thresholds from bunfig.toml
bun test src/agent/folder.test.ts    # Run a single test file (bypass wireit)
bun test -t "pattern"        # Run tests matching a name pattern
bun run build                # Full build (ESM + .d.ts + 5 platform binaries)
bun run ci                   # lint + build + test:coverage
bun run ci:nocache           # Clean dist/ then run ci (useful when debugging cache issues)
bun run install:local        # Build + install binary to ~/.local/bin/cradle
bun run uninstall:local      # Remove ~/.local/bin/cradle
```

### Coverage thresholds (bunfig.toml)

- 90% lines, 90% statements, 90% functions
- `dist/**` excluded from coverage

### Build outputs (in `dist/`)

- `index.js` — minified ESM bundle
- `index.d.ts` — type declarations (via `tsconfig.types.json`)
- `cradle-macos-arm64`, `cradle-macos-x64`, `cradle-linux-x64`, `cradle-linux-arm64`, `cradle-windows-x64.exe` — standalone binaries (no Bun required to run)

## Releases (semantic-release)

Releases run automatically on push to `main` via `.github/workflows/release.yml` and are **scope-gated**:

- Only commits with scope `(cli)` trigger a release
- `feat(cli): …` → minor, `fix(cli): …` → patch, `<type>(cli)!: …` or breaking footer → major
- `chore(…)` never releases, regardless of scope
- Release notes filter to `(cli)`-scoped commits only
- Tag format: `cradle-v<version>` — the unscoped name, not plain `v<version>`
- Publishes `@coryrylan/cradle` to npm (`npm publish --provenance --access=public` on the packed tarball; the package ships only `dist/index.js` + `.d.ts`, no binaries). The unscoped npm name `cradle` is taken by a dormant CouchDB library
- Platform binaries are **not** attached to the GitHub release — they deploy statically with the docs site (`@coryrylan/cradle-docs`'s build depends on this package's build and copies `install.sh` + `dist/cradle-*` into its output via `copy-cli-assets.js`), and the primary documented install is `curl -fsSL https://coryrylan.github.io/cradle/install.sh | bash`; npm is the alternative. `package.json#repository` must keep matching the repo the release workflow runs in (`coryrylan/cradle`) or `npm publish --provenance` fails its repository check
- The release config lives at the monorepo root (`/release.config.js`); this package's `release.config.js` is a one-line re-export.

## Commit Conventions

Enforced by commitlint (`@commitlint/config-conventional`) at the monorepo root:

- **Types**: `chore`, `feat`, `fix`
- **Scopes**: `ci`, `cli`, `docs`
- Subject: lower-case, no trailing period, max 100 chars

## Adding a new CLI command

Add to `src/cli.ts` using the Yargs builder pattern already there:

```typescript
cli.command(
  'name [arg]',
  'description',
  yargs => yargs.positional('arg', { type: 'string', describe: '...' }).option('flag', { alias: 'f', type: 'boolean' }),
  argv => {
    /* implementation */
  }
);
```

The default command (`'$0'`) prints help via `cli.getHelp()` — keep it last-wins-safe when adding commands.

Keep the Yargs handler in `cli.ts` thin: build a plain options object and delegate to a `runX(opts)`/`planX(opts)` function under `src/commands/`. Those delegate functions take their side effects (PATH lookups via `util/which.ts`, filesystem writes, spawning) as injectable deps so they can be unit-tested in-process without touching the real environment.
